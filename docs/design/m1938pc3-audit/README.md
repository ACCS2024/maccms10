## 2. 设计问题及源码证据

### P0：手机端不是正常的响应式布局

[`public/include.html:2`](source/html9/public/include.html#L2) 只有 `user-scalable=no`，缺少 `width=device-width, initial-scale=1`；[`main.css:26`](source/css/main.css#L26) 同时设定 `body { min-width: 980px; }`。

390px 手机模拟中，布局视口实际为 980px、内容宽度为 1000px、缩放比例约 0.398。虽然首页编写了 640px 媒体查询，在此布局视口下不能按手机宽度正常触发。14px 的文字被整体缩小后，视觉尺寸可能只有约 5.6px。

处理：修正 viewport，允许用户缩放；去除桌面最小宽度；桌面按列表列对齐，手机将名称、分类和更新时间重排为单条资源内部的两至三行信息。禁止用整体缩放或单纯 `overflow-x:hidden` 掩盖问题。

### P0：首屏没有突出主要任务

桌面 1440px 下，分类区高度为 357px，公告外框高度约 934px；资源列表开始于约 1558px，首条资源内部容器位于约 1643px。

[`public/head.html:58`](source/html9/public/head.html#L58) 在公共头部直接展开全部父子分类；[`index/index.html:649`](source/html9/index/index.html#L649) 又把 11 个公告卡片全部放在资源列表之前。永久域名、镜像、承诺、播放器标识、新旧接口、备用接口和教程拥有近似相同的视觉权重。

从这些功能推断，页面至少服务“查找资源”和“配置采集”两种主要任务；这是基于页面功能的产品判断，尚无访问日志或用户访谈验证其占比。首页应同时给出清楚入口，详细配置集中到接口中心。

### P1：两条独立的卡片嵌套链

```text
公告区域
wrapper-card：白底、边框、16px 圆角、阴影、20/24px 内边距
└─ notice-card：白底、边框、12px 圆角、阴影、16/20px 内边距
   └─ copy-box：输入框、复制按钮、胶囊标签

列表区域
list：白底、边框、5px 圆角、阴影
├─ title：独立白色卡片、16px 圆角、阴影
└─ list-box / content / row
   └─ container：独立白色卡片、14px 圆角、阴影
      └─ thumbnail：10px 圆角、阴影
```

证据：[`index/index.html:181`](source/html9/index/index.html#L181)、[`:195`](source/html9/index/index.html#L195)、[`:468`](source/html9/index/index.html#L468)，以及 [`main.css:329`](source/css/main.css#L329)。

同色卡片相互包裹，会把空间浪费在边框、间距和阴影上。不可点击的公告外框还有 hover 阴影，资源行悬停又上浮，传递了过多交互暗示。DOM 的合理嵌套可以保留，需要消除的是重复的视觉容器。

处理：页面为基础画布；信息区使用标题与留白；资源使用连续行和细分隔线；输入框保留必要边界；阴影用于弹窗、浮层等真正覆盖页面的元素。

### P1：表头和内容行使用不同的对齐规则

首页表头首列为 120px，资源首列为 80px；行外还有一层 20px 水平内边距。测量得到表头起点 x=141，首条资源内部起点 x=161。即使移除阴影，表头与内容仍不能准确对齐。

证据：[`index/index.html:33`](source/html9/index/index.html#L33)、[`:71`](source/html9/index/index.html#L71)、[`main.css:376`](source/css/main.css#L376)。

处理：名称与缩略图合并为一列；桌面使用语义化表格，统一列宽；手机保留同一份数据，重排布局，避免维护两套隐藏 DOM。长标题截断应能通过详情页查看完整内容。

### P1：页面间已经存在三套列表规则

首页是四列、70 条/页；分类页是三列并附带另一套卡片样式；搜索页仍是旧版三列列表、40 条/页。

[`index/index.html`](source/html9/index/index.html) 有 151 处 `!important`，[`vod/type.html`](source/html9/vod/type.html) 有 87 处；两者分别内置了大量样式。[`vod/search.html:20`](source/html9/vod/search.html#L20) 则依赖全局旧样式。样式基线、页面补丁和 HTML 行内样式混用，导致单页调整难以传播到全站。

处理：抽出资源行、筛选、分页、空结果、复制反馈等公共组件。查询数量先保留当前业务配置；原型每页 6 条只用于展示，不代表直接改变线上分页规则。

### P1：颜色、字体和动作缺少统一规范

导航使用高饱和青色，复制使用蓝色，链接与分页使用紫蓝，承诺使用橙色，同时穿插红色文字和 emoji。主导航中的多个链接都写了 `actave`，激活态无法可靠表达当前页面。全局 [`main.css:2`](source/css/main.css#L2) 还将所有元素设置为 `margin: 0 auto`，造成布局规则难以预测。

处理：单一品牌蓝表达主要操作；警告色仅用于实际需要处理的状态；导航根据真实路由设置当前项。采用中文无衬线字体栈，明确正文、元信息和标题层级。保留独立按钮反馈，不让静态容器悬浮或抖动。

### P1：详情复制存在静态代码缺陷

[`vod/detail.html:55`](source/html9/vod/detail.html#L55) 与 [第 79 行](source/html9/vod/detail.html#L79) 在循环中输出相同的 `id="playId1"`；多播放源还会重复 `playBut`、`playCopy`、`selePId…`。另一方面，[`js/main.js:72`](source/js/main.js#L72) 使用 `#playNum` 文本控制循环并读取 `#playId1`、`#playId2` 等，详情页 `#playNum` 内却是点击量节点。

这是源码层面已确认的不一致，尚未用生产多集资源操作复现其实际影响，不能声称所有复制都已失效。

处理：以播放源容器限定查询范围，通过 `data-*` 和实际选中的行收集地址；不再依赖全局连续 ID 或点击量。覆盖单集、多集、多播放源、全选、取消全选和无选中场景。复制失败提供手动复制，成功反馈使用 `aria-live`。

## 3. 商业化界面结构

商业级交付的重点是任务清楚、行为一致、数据可信和可维护。

| 区域 | 建议结构 | 迁移原则 |
| --- | --- | --- |
| 头部 | 品牌、资源目录、采集接口、接入指南 | 业务支持链接作为次级入口；仅当前项高亮 |
| 首页提示 | 一条紧凑通知，链接到详情 | 保留有效通知，详细文案与旧公告按需展开 |
| 资源目录 | 搜索 → 当前分类筛选 → 连续列表 → 分页 | 子分类随所选父分类展开，真实分类链接仍可被访问 |
| 接口中心 | 名称、适用说明、完整地址、复制按钮 | JSON/XML/播放器标识平级；备用与历史接口折叠 |
| 镜像信息 | 接口中心中的“站点与镜像”区 | 官网地址及全部镜像继续可查，不占首页大面积空间 |
| 详情页 | 资源身份信息 → 简介 → 分来源地址列表 | 保留来源、地址、正逆序、批量复制、报错、播放入口 |
| 接入指南 | 配置步骤、分类映射、验证、迁移说明 | 保留现有教程 URL，新增页与旧入口建立映射 |
| 页脚 | 必要的支持及说明链接 | 去掉没有实际目标的装饰性链接 |

接口域名集中维护在一份配置中，避免多处模板硬编码；本次原型不判断任何线上接口的可用性。未连接监控时，不展示“全部正常”“99.99% 可用”等状态或数据。资源总数、更新时间与分类数量以现有后端输出为准。

## 4. 建议的设计约束

| 项目 | 实施规则 |
| --- | --- |
| 布局 | 主内容最大 1200px；桌面两侧至少 24px，手机 16px；各页使用同一对齐线 |
| 内容层级 | 画布 → 分区 → 内容行；常规分区不叠加阴影卡片 |
| 色彩 | 文字 `#172636`、次级文字 `#647184`、品牌 `#245bd8`、分隔线 `#e3e8ee`、弱背景 `#f6f8fb` |
| 间距 | 4/8/12/16/24/32/48px；组件内部紧凑，区块之间靠留白区分 |
| 圆角 | 控件 6–8px；缩略图 4px；浮层 12px；列表行及表头不做独立圆角卡片 |
| 字体 | 系统中文无衬线字体栈；正文 14–16px；页面标题 28–32px；地址使用等宽字体 |
| 动作 | 同一任务区一个明显的主操作，其他为普通按钮或文本操作；状态不只依靠颜色 |
| 手机 | 搜索输入至少 16px；主要操作触达区域至少 44px；长地址允许换行或手动选中 |
| 交互状态 | 当前项、悬停、焦点、禁用、空结果、复制成功与失败均有定义 |

这些是本项目建议的设计与验收目标，需在真实主题、长标题、完整分类和业务状态下继续验证。

## 5. 工程落地顺序

### 第一步：建立可回滚基线，约 0.5–1 个工作日

以已拉取的线上版本为基础，建立独立主题副本，例如 `m1938pc3_v2`，保留 `html9`。记录启用模板配置、源文件哈希和现有 URL；核对首页、分类、搜索、详情、播放、教程、分页及各采集入口。新目录内资源路径使用 `$maccms.path_tpl`，排查旧主题绝对路径。

先在隔离预览环境渲染真实模板。使用生产配置的副本时，只带测试必要的配置；不依赖直接修改生产文件来预览。

### 第二步：完成目录页最小闭环，约 1.5–2 个工作日

新增共享的 `tokens.css`、`layout.css`、`components.css`、`catalog.css` 与对应片段。新页面使用明确的 `public/include-v2`，只加载所需样式与依赖，避免旧 `main.css` 的全局规则继续污染新组件。

迁移首页、分类、搜索三页，共用资源列表、分类和分页。保留 `maccms:vod`、`mac_url_type`、`mac_url_vod_detail`、`pageurl` 等服务端查询及 URL 生成行为。主列表保持服务端输出；原型的前端筛选不能直接替换生产搜索。

修正 viewport 与移动布局；对已迁移组件删除原内联 CSS 和高优先级补丁。未迁移页面继续走原有 include，待整体验证后统一收敛。禁止用 `* { box-shadow:none!important }` 之类的全局补丁快速“去卡片”。

### 第三步：接口、指南与详情页，约 1.5–2 个工作日

建立接口配置与名称映射，迁移所有主、备、新、旧接口及播放器包下载链接，保留说明和原始业务地址。原型中的示例地址不能进入正式配置。

新增接口中心与指南的实际路由和菜单，旧链接保留可访问。详情页重构分来源地址列表，修复选择和复制范围。统一 Toast、错误反馈、弹窗焦点返回和键盘操作。

### 第四步：真实数据回归与发布，约 1–2 个工作日

桌面和手机验证完整分类、超长标题、缺失图片、搜索无结果、多页结果、多播放源和错误反馈。确认缩略图尺寸占位与懒加载，避免不必要的图片加载；测量真实页面加载数据，本次不根据屏蔽图片的审计会话给出性能结论。

建议由一名前端/模板工程师完成主改造，并安排熟悉业务的人核对接口及验收，总体估计 5–7 个工作日。估计不包括额外功能、后端搜索重构和新的后台配置管理界面。

正式发布采用版本目录与模板配置切换，并按实际 ThinkPHP/MACCMS 缓存配置清理相关模板缓存。发布后检查主要页面和关键交互；异常时切回旧主题并重新生成相应缓存。若改动路由或公共组件，必须与主题版本一起回滚，不能只切模板名。此处是发布方案，本次未执行切换。

复现依赖：Node.js、Playwright 包、Chromium（脚本默认 `/usr/bin/chromium`）。本次使用临时工具目录中的 Playwright；原型本身无第三方网络依赖。

```bash
NODE_PATH=/tmp/maccms-theme-audit-20260909/browser/node_modules node docs/design/m1938pc3-audit/evidence/verify.cjs
```
