# 创建订单时的精确金额与积分

## 已确认问题

充值入口 `index/User::buy()` 和 `API/Order::create()` 原来先转换浮点再取整数。例如 `0.29 * 100` 的浮点结果可能略小于 29，`intval()` 得到 28；超大倍率或金额也可能产生零积分、积分溢出或数据库截断。API 的两位小数金额校验不能约束乘倍率后的 `order_points`。

会员现金订单原来把倍率先 `intval()`，导致小数倍率被截断；极高倍率还会使正积分套餐报价四舍五入为零。会员订单保存了固定 `upgrade_points`，支付后将同样的订单积分入账再扣除，因此不能按充值规则从现金价重新计算积分。例如 1 积分、倍率 3 的会员订单合法报价为 0.33 元，积分快照仍为 1；相同金额的纯充值会得到零积分，必须拒绝创建。

## 统一后的规则

`application/common/util/OrderAmount.php` 使用有界整数运算，无 BCMath 依赖。部署需要 **64 位 PHP**，低于 64 位时计价方法拒绝处理。

| 输入或行为 | 规则 |
| --- | --- |
| 金额 | 对齐 `DECIMAL(12,2)`，最多 10 位整数、2 位小数，必须为正；拒绝指数、符号、空白、非法容器、非有限值、额外精度。已有浮点调用只在两位小数能准确往返时接受。 |
| 充值倍率 | 正十进制，最多 10 位整数、8 位小数；保留原充值实际支持的小数倍率。拒绝缺失、零、负数、非法格式，不默认改成 1。 |
| 充值积分 | 精确计算 `floor(金额 × 倍率)`，须在 `1..16777215`，在乘法和写库前检查上界。 |
| 会员现金订单 | 服务器套餐积分须在 `1..16777215`，保存固定积分快照；现金价精确按半入规则保留到分，零报价或超过金额列上界均不可下单。 |
| 免费会员 | 既有余额升级接口仍允许显式配置的零积分套餐；展示允许零价，不需要现金支付倍率。现金订单创建不接受零积分。 |
| 最低充值金额 | 缺失或空值表示无额外最低值；已配置值按同一金额规则校验，精确比较到分。非法值阻止充值，不靠 PHP 类型转换。 |

充值两入口和会员现金订单统一调用该工具；仅 API 充值 `create()` 补上 POST 限制。`Order::notify()` 的原私有金额解析委托同一工具，回调结果、金额一致性和幂等边界不变。

`API/Payment` 已逐方法扩查，没有创建 `Order` 的路径：`gopay()` 读取既有订单，`upgrade()` 和 `use_card()` 委托已有模型。其 `get_config()` 本次只同步精确最低金额和真实小数倍率，避免展示侧再次 `intval()`。余额购买内容的事务属于后续独立审计。

订单创建接口中的 `order_price` 返回规范的两位小数字符串，与数据库 DECIMAL 值一致；支付配置的 `min` 同样返回字符串，`scale` 保留校验过的配置数值。调用方应将金额作为十进制字符串传递，不依赖二进制浮点做结算。

会员报价 API、旧模板四个周期与动态模板同步：合法现金报价展示相同价格；不能现金报价的周期返回 `null`，界面显示“仅支持积分兑换”，仍保留既有积分余额升级和免费套餐操作。现金支付配置损坏不会隐藏余额套餐。

## 下一独立资金边界

创建输入的积分上界不能保证“已有余额 + 新积分”不会溢出。在 MySQL 非严格模式下，订单入账、推荐奖励等余额加法仍需证明不会被截断，并应使用原子余额上界条件。这一问题单独修复，不用数据库严格模式代替业务边界。
