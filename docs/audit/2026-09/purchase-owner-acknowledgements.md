# 内容购买事务的异常收尾（F1a）

日期：2026-09-10。适用于已接入锁内报价的 Video、Art、Manga 购买；普通 `ContentPurchase::buy` 的调用方事务兼容路径另列 F1b。本批不把其它金融方法或附件事务纳入完成范围。

## 已确认问题

旧协调器在业务分支调用回滚，回滚抛异常后又进入 catch 再次回滚。真实 PDO 证明这可以多退出一层调用方事务；直接在 catch 调用回滚也可能让原始业务错误变成未捕获异常。ORM 的事务深度会在部分底层操作之前改变，单个 `$started` 标记无法描述 BEGIN/ROLLBACK/COMMIT 前后异常。

另一个容易遗漏的情况是：被调用的事务代码已经结束原事务，然后抛异常。此时仅观察 PDO 已不在事务中，不能推断操作已经回滚；原型增加了先提交普通余额变化再抛错的对照，确认必须返回未知结果。

## 当前处理

新的 `PurchaseTransaction` 先强制选取主库，保存原连接与 PDO，并确认调用之前没有事务。诊断编号和专用文案在开始前准备。启用 `break_reconnect` 的连接会在购买开始前受控拒绝：本批要求财务 owner 不自动换连接，未修改全局连接器设置。

BEGIN 尝试在调用前标记；报价前后、返利之后和最终提交前核对事务身份。回滚只调用一次 ORM；若原始 PDO 仍有事务，仅对这个明确归本次购买所有的原句柄做一次有限补救，并重置损坏的连接深度。不会回滚替换后的连接或调用方已有事务。`close()` 只是移除 ORM 引用与深度，不被当作物理回滚的证据。

只要最终 COMMIT 曾尝试却没有确认，即使随后清理成功也返回 `2004 / commit_unknown`。无法确认清理或发现原事务身份/状态被改变返回 `2005`。两者均带 `info.retryable=false` 和诊断编号；日志只记录该编号、状态及已规范化的账号 ID/购买坐标，不记录密码、Cookie、原异常文本或连接凭据。九种语言均提供先核对购买记录、勿重复付款的专用文案。

未知结果会阻止当前 Request 再次调用 owner 购买；后续响应沿用同一个诊断编号。不同 Request 实例不继承这一阻止状态，避免进程级布尔值误伤长驻进程后续请求。既有客户端显示服务端文案，不因未知结果自动重试、刷新页面或发起充值。

正常成功、已购买、余额不足及可确认完全回滚的错误保持原响应合同。扣费、消费账本、返利及购买凭证仍由原有业务代码写入同一个事务，本批不改价格或返利规则。

## 验证

`tests/framework_audit_purchase_owner.php` 使用真实 PDO、ORM 与普通事务操作，仅在调用前后注入确认失败。SQLite 使用独立文件以跨连接观察最终存储；MySQL 使用独立 `maccms_audit_owner_purchase`、安装 DDL 和非严格模式。覆盖 BEGIN、ORM/PDO 回滚、提交前后异常、嵌套返利事务、保留原始外部 PDO、连接替换、调用方外层事务和 Request 范围。

专项每 PHP/数据库组合 108 项；另运行双版本现有 models/financial、MySQL 对应回归和实际 PHP/Chromium 六种购买客户端。前端方法与默认升级组件的普通返回值测试增加未知结果检查，共 282 项。物理数据库的最终余额、全部返利账本及凭证一同断言，不以单条凭证代替整笔事务的一致性证明。

## 后续边界

本批没有增加跨请求的持久购买操作 ID、自动核对器或补偿流水。未知结果需要结合完整账户、消费/返利账本与凭证核对，不能因某条 Ulog 存在就自动宣布整笔操作成功，也不能自动按新价格重试。未来跨请求的恢复机制须单独设计和迁移。

普通 `buy` 的 SAVEPOINT 收尾仍待 F1b；当前仓库生产入口已使用三个 owner 报价方法，普通方法继续保留旧兼容合同。其它金融方法、独立调用的返利服务、外部保留的原始 PDO，以及附件 BEGIN/ROLLBACK 异常仍需各自审计。本批仅隔离当前 Request 的内容购买动作，不宣称封锁了整个应用的所有数据库调用。
