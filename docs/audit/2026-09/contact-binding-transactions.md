# 联系方式绑定、解绑与验证消费

## 行为变化

旧 `bind` 在匹配验证码后会清空所有持有目标邮箱或手机的账号，再写入全局用户编号；验证码没有消费记录，也没有事务。`unbind` 只接收渠道即可清空联系方式。API `update_info` 还可以绕过验证直接写邮箱或手机，导致依赖非空联系方式的新手任务提前完成。

本组把绑定身份改为真实 `User::checkLogin()` 返回的已启用账号，独立传入消息发送和匹配方法。请求中的 `user_id`、全局展示用户、调用者提交的消息用途均不能选择被更新的账号或验证码用途。绑定固定使用用途 1；收件人、渠道格式、用户、有效期和未消费状态同时匹配。

SQLite / MySQL InnoDB 的同一事务内锁定本人账号，检查目标尚未被绑定，条件消费验证码，然后在同一条用户更新中写入联系方式与新的 32 字符会话随机数。任一步失败回滚。其他账号的联系方式始终不清空，已有绑定必须先明确解除。旧 JWT / Cookie 因随机数变化失效；成功响应包含 `reauthenticate: 1`，需要重新登录。

解绑采用“已登录身份 + 当前密码确认”，只读取本人数据库中的联系方式，并在事务内清空所选字段和旋转会话随机数。保留历史 MD5 密码的既有兼容匹配；现代密码使用原始字节。密码遗忘者可通过现有邮箱/手机找回流程重设密码后再解除。没有新增短信用途或配送模板。已经为空的联系方式，在重新认证且密码正确时返回幂等成功，不重复改变会话。

绑定验证码验证与解绑密码确认分别受现有 IP 写入限频器限制（10 分钟 10 次）。发送验证码沿用现有发送限频。非事务表在发送和修改之前返回受控失败。

## 浏览器与 API 入口

| 路径 | POST 正文 | 作用 |
| --- | --- | --- |
| `index.php/user/bindmsg`、`api.php/user/bindmsg` | `ac=email|phone`、`to` | 向尚未占用的目标发送绑定验证码 |
| `index.php/user/bind`、`api.php/user/bind` | `ac`、`to`、`code` | 消费验证码并绑定本人联系方式 |
| `index.php/user/unbind`、`api.php/user/unbind` | `ac`、`user_pwd` | 用当前密码确认解除本人绑定 |

写入参数只读 POST 正文，查询字符串不能补齐或覆盖字段。API 写入口全部拒绝 GET；前台 bind/unbind 的 GET 仅显示页面。两页保留 Base 注入的共享模板参数，避免覆盖后导致头部 `wd` 或底部 `sid/nid` 缺键报错。

此前 `CsrfGuard` 只保护后台。本组对 Cookie 认证的三个联系方式写入口检查稳定的会话 CSRF 令牌：POST `csrf_token` 或 `X-CSRF-Token`，必须匹配 Session `__csrf_token__`。三个主题的表单通过现有 `mac_csrf_token()` 生成令牌。显式 Bearer JWT 经真实认证通过后使用凭据本身，不要求浏览器会话令牌。

default 的 `user-bind.js`，以及 demo / m1938pc3_v2 的内联绑定脚本，继续发送正常序列化表单。邮件前端校验支持合法的加号地址和长顶级域名，后台格式规则保持严格。三个主题的资料页解绑链接改为进入新增的密码确认页面，共用 `static/js/user-unbind.js` 提交和跳转登录。

API `update_info` 对任何实际邮箱/手机变化拒绝整个请求，并指向绑定入口；完整资料表单回传未变化的联系方式时忽略这些回显字段，其余资料仍可正常更新。共享 `updateAccountProfile` 也拒绝联系方式字段，防止其他普通资料路径再度绕过验证。本组不把旧数据库中的已有非空联系方式自动认定为新验证记录。

## 并发与边界

现有安装 DDL 没有邮箱/手机唯一索引。MySQL 绑定使用数据库、用户表、渠道与规范化目标组成的 SHA-256 命名锁（64 字符、等待上限 5 秒）；取得与释放均强制使用同一主库连接，所有退出路径释放。该锁串行化本组绑定调用，随后才开始事务和行锁检查。SQLite 使用事务与条件更新。

命名锁不等于数据库唯一约束：尚未迁移的注册、后台资料写入等独立写入者仍需在下一组协调相同锁，最终应先清理历史重复联系方式，再迁移数据库唯一性保障。本组不会在没有数据预检时擅自添加唯一索引，也没有修改注册、OAuth 创建、邀请或访问奖励方法。
