# AI 内部资源查询的 ORM 兼容与结果一致性

本批生产范围仅 `application/common/util/AiSearch.php`。当前调用来自 `AiChatService::buildPayload()`，资源查询涉及视频、文章、漫画、专题、演员、角色、网站七张表；剧情复用视频表和视频详情 URL，返回的 `type` 为 `plot`，SQL 使用剧情名称/详情字段匹配。未修改 AI 聊天其他卡片查询、共享公开查询助手、搜索建议、外部聚合或实际 AI 请求。

## 修复内容

`queryResourcesByMeilisearch()` 原先把实际 ORM `Collection` 交给 `is_array()` 判断，正常数据库命中也返回 null，调用者转入 SQL。现在显式 `toArray()`，依索引 ID 顺序映射真实数据库行，恢复索引排名。只取固定展示字段，保持 `title/url/pic/type` 和原详情 URL 构造器；专题 ID 依实际 DDL 使用 UINT16 上限，其他模块使用 UINT32，上限内的真实记录可正常返回。

七模块加剧情的 SQL 回退和索引回表共用一个私有查询助手。业务行始终从 writer 读取，必需的 ID/status 字段也通过同一 writer 的参数化只读 schema 查询确认。所有模块要求 `status=1`；当前安装表中视频、文章、漫画另要求回收时间为 0。只有实际表的必需字段已确认且回收列确实不存在，才兼容旧 schema。无法确认表、字段或查询失败时抛出错误，不再移除回收条件重试。已有 AiChatService 调用处保留其可选 AI 元数据的异常处理，本批未新增面向用户的接口错误码或修改该调用者。

每次仅探测选中模块的一张表。正常资源查询一次 schema 确认；专题等模块在空回表后转 SQL，最多对同表确认两次。不遍历其他六张表，不缓存跨连接 schema 证据，也不执行迁移或 DDL。测试中的真实读写分离连接验证了字段发现和业务行都来自主库，不依赖副本是否已同步。

原来的整个 payload 静态缓存改为只保存扩词。重复构建时重新查询当前公开资源，避免继续使用已撤回、回收或删除的行；MeilisearchService 自己的请求内索引结果缓存仍生效，正常重复调用没有增加外部传输。代价是每次增加所选模块的 schema/行读取，而不是复用旧公开状态。

## 保留的业务合同

| 情况 | 结果 |
| --- | --- |
| Meili 未启用、服务返回不可用、无任何 hits 或有效 ID | 原 SQL 回退 |
| 有索引 ID，但视频/文章/漫画回表没有公开行 | 空数组，不再查询 SQL；剧情随视频 |
| 有索引 ID，但专题/演员/角色/网站回表没有公开行 | SQL 回退 |
| SQL 命中 | 原匹配字段，`hits desc,id desc`，最多 8 条 |
| Meili 命中 | 原排名，使用 `internal_result_limit`；缺省 8，至少 1，既有服务最多 1000 |

上述空回表差异来自原元数据 `return_null_when_empty` 的既定分支；Collection 修复使其能够按预期执行。没有为剧情额外引入 `vod_plot=1` 限制，因为本方法原来返回的是公开视频链接，剧情仅区分匹配字段和结果类型。

## 仍待独立处理

- SQL 固定 8 条与 Meili 可配置数量不一致。本批没有找到说明要求 SQL 也按该配置扩大数量，故保留原负载合同，后续单独决定统一规则。
- 其他 AI 卡片、搜索建议、公开列表的状态、schema 缓存和主从策略不因本助手修改而自动覆盖。
- 扩词配置、输入归一化、外部服务生命周期和整份 AiChatService 不在本批范围；扩词缓存保持原查询键语义。
- 本批全矩阵在 MySQL 上运行；助手包含 SQLite 的只读 schema 分支，但未宣称已完成 SQLite 全矩阵或真实 Meili 服务验证。
