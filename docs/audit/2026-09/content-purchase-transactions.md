# 内容购买事务协调

前台 `ajax_buy_popedom` 和 API `payment/buy_popedom` 原来各自执行扣款：在事务前查购买记录、读取请求早期余额；部分账本与购买记录失败返回码被忽略，API 分销还未显式传入已经认证的来源账号。同一资源的并发请求可能各自扣款。

本组将两处事务实现收敛到 `ContentPurchase::buy`，价格仍由控制器读取服务器内容配置，客户端提交的价格和会员编号不能作为扣费依据。输入先校验实际支持的模型/操作组合及整数字段，避免跨模型选择错误的价格表。前台保留视频、文章、漫画；API 保留其既有视频、文章范围。

事务先锁定实际买方账号，再对购买凭证执行锁定读取，然后根据当前余额扣款。购买唯一语义沿用当前权限查询中的会员、模型、操作、资源、sid、nid与价格组合。MySQL 并发回归证明，仅锁余额行但普通读取凭证仍可能读取旧快照：初版四个同资源请求全部返回成功且各扣20；改为凭证锁定读取后，四个请求均返回可用结果，总共只扣20并仅创建一套凭证与分销账本。SQL 和独立进程证据保存在本地审计目录，不依赖线程顺序假设。

买方扣款与消费账本、三层分销奖励、购买凭证使用同一外层事务；余额和账本都要求逐字段读回一致，任何返回失败、异常、旧窄字段截断都回滚。MySQL User/Plog/Ulog 任一非 InnoDB 时在写入前拒绝。合法零价只创建零价凭证，不扣款或制造消费/分销账本。余额不足返回锁定后的实际余额。若调用者已有外层事务，最终提交权仍属于调用者。

`tests/security_audit_content_purchase.php` 使用真实 User/Plog/Ulog 模型，验证重复、免费、余额不足、失效用户、类型/容量、各层账本拒绝和异常、存储故障以及嵌套回滚。MySQL 使用真实安装 DDL、非严格模式，另有三表引擎、两种窄字段和四个独立 PHP 进程的同资源/不同资源/余额不足竞争。两处控制器方法还使用真实 MySQL 身份验证和实际事务协调器验证正常扣费、重复和错误参数；该局部控制器检查仅替换内容元数据查询，未经过应用 HTTP 中间件。

PHP 8.3/8.4 专用检查为 SQLite 78、MySQL 110 项，已纳入独立串行的 `financial`。测试只使用 `maccms_audit_membership` 的隔离表，不使用生产配置或真实支付。

## 紧接的闭环工作

这是事务批次，不能据此认定完整内容购买已可上线：

- 前台实际购买客户端目前仍使用 GET，本批保留可达性；下一客户端批次必须同时改 POST 正文与 Cookie CSRF，验证真实主题，不能单改服务端导致无法购买。
- 当前控制器仍沿用原资源查询/价格提取和坐标约定。Vod 授权组的统一真实章节与价格解析提交后，购买端必须接同一解析器；文章分页、漫画章节随后按各自授权链统一。不可用资源/权限校验还需覆盖完整业务入口。
- 行为日志的删除接口仍可能删除购买凭证；购买记录与展示历史的保留/隐藏方案必须独立完成。实际价格变更后旧价格凭证不匹配的现行业务规则暂未改变。
- 静态生成文件、历史截断凭证和旧重复扣款需要独立部署/数据处理方案；本批不自动删除文件或调整历史金额。
