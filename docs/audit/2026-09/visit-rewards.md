# 推广访问奖励的事务与额度

`User::visit` 原先在事务外查询当天次数，再依次保存访问、增加积分、写账变。后一步失败不会撤销前面的写入，不存在的用户也可能得到成功响应；并发请求能同时通过次数检查，非严格 MySQL 还可能截断余额。

修复在同一事务内先锁定受益用户，再检查该用户/地址的当天次数、保存访问、执行带上限的积分增加及检查账变结果。任一步失败均回滚；不存在的用户、无效参数和非事务表拒绝发奖。日期区间包含当天零点，排除次日零点及未来记录。零奖励保留访问次数，但不制造金额为零的账变。旧配置的空值或零次数继续解释为每天一次。

积分使用实际安装结构的 `INT UNSIGNED` 上限；旧 `SMALLINT` 账变在非严格模式下发生截断时，读回检查使整个奖励回滚。来源文字按原有 HTML 转义后限制为表结构的 100 字符。服务器生成用户、地址、时间、积分和账变类型，不接收调用方代填这些字段。

回归 `tests/security_audit_visit_rewards.php` 使用真实 User/Plog/ORM，SQLite 默认运行，MySQL 使用 `MEMBERSHIP_AUDIT_MYSQL=1` 的专用测试库和安装 DDL。覆盖正常访问、次数与日期边界、完整 UINT32 金额、余额溢出、插入/余额/账变失败回滚、事务开始前的竞争，以及另一条 PDO 连接对受益用户的真实锁等待。MySQL 另验证非严格模式、三张表逐一改为 MyISAM 后拒绝发奖、旧账变列截断。

这里保证的是账务与次数的一致性，不证明访问者是真人或推广有效。现有 IPv4 整数结构仍将未知地址/IPv6 归入零地址桶；IPv6 地址建模、推广防刷策略、后台访问记录留存和奖励撤销政策需另行处理。管理员直接删除当天的访问凭证仍会影响次数统计，因此不能把本次修复表述为全链路防重复已经完成。
