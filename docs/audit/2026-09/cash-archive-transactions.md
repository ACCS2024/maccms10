# 提现归档与退款原子性

原先删除提现记录后，收款字段、申请金额和原始状态从业务库消失。现在新增独立 `cash_history`：保存完整原记录 JSON（包括历史扩展列）、SHA-256、原提现编号、账号、最终处理状态、归档时间和操作者类别/编号。待审核申请取消后归档状态为 2，已付款记录归档状态为 1；JSON 保留处理前的原始字段及类型。

归档与退款、活动记录移除共享原始 PDO 事务，归档表必须为 InnoDB。模型先锁定提现记录，再按账号顺序锁定并记录整批原余额；任何归档失败、被改写、后续触发器改变余额/历史记录或删除失败都会回滚。提交前再次检查全部归档和最终余额，避免后续行的写入覆盖前一行的验证结果。已付款记录移出列表不退款；普通记录操作不删除已归档的快照，也不删除请求幂等凭据。

会员端传入重新验证的账号，管理端传入当前已授权管理员；请求参数不能声明操作者。旧内部调用明确记为 `internal/0`，不猜测历史操作者。主键禁止重复提现编号覆盖旧档案；超出 16 KiB 的历史扩展数据保留在活动表并拒绝本次操作，避免截断后删除原件。显式选择及 `all=1` 都受实际 1,000 条批次上限约束；超限在资金操作前拒绝，审核使用相同批次上限。

已有站点通过 `migration/create-cash-history.php` 默认只读预检，再按发布流程执行 `--apply`。参数为 `CASH_HISTORY_SCHEMA_DSN`（明确 MySQL 数据库）、`CASH_HISTORY_SCHEMA_USER`、`CASH_HISTORY_SCHEMA_PASSWORD` 及可选 `CASH_HISTORY_SCHEMA_PREFIX`。脚本只新增归档表，不在 HTTP 请求时建表、不修改历史数据；新安装 SQL 同步包含该表。代码发布前完成新增表迁移。回滚到旧删除逻辑前须停止相关写入并保留归档表和请求凭据。

验证覆盖真实 SQLite/MySQL、普通/已付款记录、会员/管理员/内部来源、历史 Unicode/换行字段、重复编号、批次边界、主库独立观察连接及原始 PDO 故障。失败快照包含归档表，不能凭“活动表和余额正确”掩盖孤立归档。SHA-256 用于读取完整性和实际存储核对，不宣称能抵抗拥有数据库写权限者同时重写数据及摘要。

本批先完成保存与事务，后台只读归档查询作为紧接的独立提交。生产迁移、历史备份恢复及外部付款对账仍未执行。
