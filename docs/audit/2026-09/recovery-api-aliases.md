# 旧找回密码发送 API 的字段与用途

`api.php/user/find_password` 的文档要求 `user_email` 或 `user_phone`，实现却把原始参数交给 `reg_msg`。文档中的正常请求缺少底层所需 `ac/to`，无法正常发送；补上这些参数的请求又会写成注册验证码，不能用于找回密码。

本组仅修改 `API User::find_password`。接口现在要求 POST 正文，将一个非空邮箱或手机号别名映射到 `ac=email|phone` 与 `to`，调用既有 `findpass_msg` 固定写入 `msg_type=2`。同样支持标准 `ac/to` 请求；重复提供字段时必须一致。两个非空联系方式、别名与渠道不符、收件人不符、数组/null 等错误类型都在发送前拒绝。仅 trim 原始文本，不重复 URL 解码。URL 不能补齐或覆盖正文，客户端 type、用户 ID 和其他字段不会被传给发送模型。

渠道格式、验证码随机生成、有效时间、收件人、冷却时间、发送限流和消息保存继续复用已审计的共享模型。账号密码与会话不会在发送阶段修改；发送失败或消息写入失败返回错误，不伪报成功。外部发送与数据库保存并非一个可回滚事务，故数据库失败时可能已有一封无法用于重置的消息送达；本组保持原有明确失败语义，不声称外部消息可以回滚。

现有默认主题页面和 AJAX 弹层使用 `index/user/findpass_msg` 及 `findpass_reset`，没有发现调用此旧 API 的模板。本组不修改它们或重置终点。新增测试通过实际 API 路由、真实 User/Msg ORM 和隔离发送函数，取得本接口生成的实际验证码后调用未修改的重置模型，验证用途与收件人兼容、验证码消费及真实新密码哈希。

`tests/framework_audit_find_password.php` 覆盖正常别名/标准字段、错误渠道和冲突、严格 POST、结构化字段、格式错误、请求附加字段、重复发送、限流、模拟发送失败及消息表触发器写入故障。所有发送只记录在 fixture 内，账号与数据库完全隔离，不接触生产邮箱、手机号或消息服务。

PHP 8.3/8.4、SQLite/MySQL 非严格模式四个组合均通过 172 项检查；MySQL 使用相同安装 DDL。
