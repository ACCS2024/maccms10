# 订单当前值与实际入账核对（F2d）

日期：2026-09-11，基于 `9fd9e21a` 的独立修复批次。

## 实际证据

固定源 `251e851b` 在两版 PHP、SQLite/MySQL 中均复现：订单的 user_id、order_points、order_code 或 order_remarks 在 BEGIN 前被普通并发编辑后，旧回调仍以最初快照成功入账。例如订单已换为用户 2，实际充值及会员升级仍给用户 1；订单改为 40 分，实际只充 20 分；移除会员用途后仍升级会员。两版非严格 MySQL 均确认 300 分充值完整入账，但 TINYINT 台账只保存 255，仍返回 code 1。F2c 只改变事务拥有关系，没有借用它的结论关闭这些问题。

## 修复

回调在 BEGIN 后从主库锁定当前订单，按当前订单决定收款用户、积分和会员用途，重新校验实际金额。读取至多两条以识别旧库缺少唯一索引时的重复订单号，歧义一律不入账；请求不执行迁移。已支付回放在锁内确认金额后结束只读事务。

锁定当前用户并核对余额上限，充值、会员及返利完成后核对实际订单身份/金额/用途/支付状态/渠道/时间、充值台账用户/类型/积分/备注及最终余额。受影响行数为 1 不能替代实际持久值；非严格截断或普通触发器改变财务字段均整笔回滚。回调订单号最多 30 个 UTF-8 字符、渠道最多 10 个，与安装列一致；类型、字节容量、编码和控制字符在查询前验证。可信自定义渠道省略金额的既有兼容路径保留。

## 验证

PHP 8.3.33 和 8.4.25 各自通过：

| 范围 | 结果 |
| --- | --- |
| 改动 PHP 编译、默认金融套件 | 22 个金融进程，零失败 |
| 新当前订单/落库回归 | SQLite 78、安装 MySQL 非严格模式 80 项 |
| 原支付 owner 故障 | SQLite 252 / MySQL 255 项 |
| 原金额、幂等、会员回调业务 | SQLite/MySQL 各 158 项 |
| MySQL 会员 / 余额溢出 / 支付 schema | 51 / 29 / 43 项 |
| 两独立回调同时 BEGIN | 每版 20 项、4 个独立工作进程 |
| 六个渠道签名/响应回归 | Alipay 31、Weixin 40、Epay 31、Codepay 25、Zhapay 26、Jeepay 37 项 |

并发检查在独立 `maccms_audit_order_parallel` InnoDB 数据库中运行，各工作进程到达实际 Connection BEGIN 前的屏障后同时放行，普通充值与付费会员均只写一份充值及关联台账、只返利一次。其它实际编辑/截断检查使用 `maccms_audit_order_storage`。没有访问生产库或真实支付商。

持久入口：`tests/framework_audit_order_storage.php`（已加入金融套件）、`tests/framework_audit_order_concurrency.php`（显式 MySQL）。原始证据在 `/tmp/maccms-audit-20260910/order-followups/storage-*.log`、`concurrency-check1.log` 和验证树文件。F2c 的双版 33 模型进程结果只对应该批，F2d 使用本表专项结果。

## 后续边界

既有已支付但历史台账不一致的数据需要人工/专用核对，不会因再次回调而自动改写。跨请求诊断持久化、异常会员备注的兼容/拒绝规则、完整主从拓扑故障演练、死锁重试策略及其它资金入口的事务收尾仍待审计。并发检查证明当前 InnoDB 正常重入合同，不宣称覆盖全部故障组合。
