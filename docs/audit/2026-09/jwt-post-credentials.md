# JWT 登录入口正文与验证边界

`api.php/auth/jwt` 原来虽然要求 POST，但使用 `Request::param()` 混读查询串与正文。缺失的正文密码或验证码可能由 URL 补足，也使凭据进入访问日志的风险难以避免。本组仅修改该控制器的 `jwt` 方法：先确认 POST，再从正文读取用户名、密码与验证码；提供了错误类型的字段（包括 null、数组、布尔值）直接返回受控错误。

入口继续调用共享模型的 `set_cookie=false/return_meta=true` 服务端契约，保持原始密码、历史 MD5 兼容、配置要求的验证码、登录限流和事务会话更新。HTTP 请求里的用户 ID、OAuth 选项、身份列或返回选项都不能改变认证身份。成功响应仅包含 bearer token 类型、签名后的 access token 和有效期，不创建浏览器 Cookie。

JWT 的启用开关、密钥、issuer 和 TTL 类型在登录之前检查。坏 issuer 或结构化配置值不能在模型已更新密码/会话之后才引发签发异常。已有有效配置行为保留：密钥强度仍由 `JwtService` 判断，默认有效期与 300 秒至 30 天的范围沿用现有服务。预检还会用实际签发器和校验器生成最大 DDL 用户 ID、32 位新会话随机数对应的候选 token，确认它满足现有 8192 字节上限；因此包含 Unicode 或引号转义的 issuer 按实际 JSON/Base64 后大小判断，不另设短字符上限。该预检限定当前入口；没有更改共享 `JwtService` 或本组之外的认证路径。

新增 `tests/framework_audit_auth_jwt.php` 通过实际 TP8 路由、真实 User ORM 与签名服务验证：正常 POST、URL 无法补充/覆盖凭据、缺字段/错误类型、登录验证码、历史密码升级、不可用账号、限流、坏签名配置、有效期边界以及写入失败回滚。签发后的 token 通过真实 `User::checkLogin()` 验证，第二次正常登录会使前一 token 失效。数据库写入故障时保持旧密码与会话，不返回 token；解除隔离故障后同一合法请求可重试。

PHP 8.3/8.4、SQLite/MySQL 非严格模式每组合均通过 128 项检查。数据库复用专用注册审计库与实际安装 DDL，测试密钥和账号完全隔离，没有外部身份服务、邮件、短信或生产凭据。R3 冻结模型和其他入口保持不动；同期 R3 身份列修正由主任务单独审阅提交。
