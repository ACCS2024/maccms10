# 内容购买浏览器请求闭环

本组接通 Cookie 登录用户的实际购买页面：六份首页脚本的 `MAC.User.BuyPopedom` 和默认主题会员门按钮原先通过 GET 查询串调用购买入口，现在先同源获取 `GET /index.php/user/write_token`，随后将 `mid/id/type/sid/nid/csrf_token` 全部放入购买 POST 正文。路径从当前站点安装目录构造，支持根目录和子目录部署，不向配置的其他域名发送请求。

新增的 `MAC.User.BuyPopedomRequest` 被普通购买确认与会员门共用。每次尝试重新获取令牌，令牌仅存在当前请求的闭包和 POST 正文，不放入 URL、Cookie 或浏览器持久存储。读取令牌和提交均设置超时；缺令牌、错误 JSON、HTTP 失败和业务拒绝都恢复按钮状态，保留服务端可读错误。按钮忙碌状态覆盖两个请求阶段，防止同一个按钮连续点击产生并行购买。请求失败后由用户明确重试，不自动重发积分交易；跨按钮、跨页面或网络响应丢失情况下的重复扣费控制仍由后端购买事务负责。

默认主题保留原确认交互、成功提示及页面刷新，会员门保留未登录时登录弹窗、余额不足时充值弹窗和充值页回退；同时识别 index 的 2002 和 API 的 1005 状态码，英文提示也能正确引导充值。视频、文章和漫画模块参数保持一致，漫画继续使用 `mid=12`。另外修正两处实际入口：默认视频播放器按钮使用正确的 `window.parent` 并补 `data-mid=1`；m1938 下载播放器按钮同样补视频模块参数。

六份脚本是 `static/js/home.js`、`static_new/js/home.js`、`template/m1938pc3_v2/js/home.js`、`template/vozy/tuo/assets/mac.js` 及默认主题的 `user-home-stack.js/public-home-stack.js`。只替换购买方法并插入共用方法，没有重新生成整个 bundle。实际模板中 18 个相关脚本引用更新为 `v=202609102`，让已有浏览器获取新购买代码；同一文件中的登录、密码验证和其他同期修改按各自方法边界保留。

验证分三层：

- `tests/framework_audit_purchase_frontend.js`：Node VM 执行六份实际方法及会员门实际回调，共 254 项检查，覆盖确认取消、两阶段重复点击、坏令牌响应、网络错误、手动重试、同源约束、正文参数及充值回退。同期默认登录回调 30 项回归仍通过。
- `tests/browser/purchase_csrf.cjs`：真实 Chromium 加载仓库 jQuery 和上述实际方法/会员门脚本，向隔离的本机 HTTP 服务发请求，共 173 项检查。验证实际 GET→POST 顺序、表单编码、两类 HTTP 失败后的重试、新令牌使用、重复按钮点击和漫画购买/充值交互。服务使用固定正常资源和隔离的合同响应，不模拟生产账户认证，不连接真实站点；后端认证、CSRF 与扣费事务由对应后端组的真实 ORM/路由回归覆盖。
- `tests/framework_audit_purchase_views.php`：PHP 8.3/8.4 各通过 46 项检查，用真实模板引擎渲染会员门与两处 iframe 按钮，验证视频播放/下载、文章、漫画参数，以及无资源或仅会员权限场景不会显示无效购买按钮。六份完整脚本均通过 Node 语法检查。

Chromium 工具沿用 `tests/browser/package-lock.json` 的已固定依赖；可以在临时目录安装依赖并通过 `NODE_PATH` 执行浏览器测试，无需修改应用依赖或生成构建产物。本组只验证购买前端协议；没有把其他写接口的 GET 调用视为已修复。
