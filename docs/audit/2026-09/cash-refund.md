# 提现退款的余额上界与原子性

## 已确认问题与修复

`Cash::delData()` 原本在同一条 UPDATE 中增加可用积分、减少冻结积分，但仅检查冻结积分是否足够。安装 DDL 的 `user_points` 和 `user_points_froze` 都是 `INT UNSIGNED`，上限为 4,294,967,295。非严格 MySQL 会把超限余额截断为上限，而不抛异常；后续代码继续删除提现记录并返回成功。

修复前已用真实安装 DDL、真实 Think ORM、MySQL 8 的 `sql_mode=''` 复现：可用余额 4,294,967,285、冻结 20、待审核提现 20，删除返回 `code=1`，最终可用余额 4,294,967,295、冻结 0、提现记录数 0。仅退回 10 积分，却消耗了全部 20 冻结积分。原始输出保存在 `/tmp/maccms-audit-20260910/cash-refund-before-php84.log`。

现在退款 UPDATE 同时要求 `user_points <= PointsBalance::MAX - cash_points`，并继续要求冻结积分足额。积分使用共享 `PointsBalance::amount()` 验证。任一条件不满足，原有事务回滚整个退款批次，保留可用余额、冻结余额和提现记录。刚好达到最大余额的退款仍允许。

源码创建、审核动作和后台筛选只定义状态 0（待审核）与 1（已审核）。删除遇到其他状态现在受控失败，避免把未知状态的冻结资金连同唯一提现记录丢弃。已审核记录沿用原有删除且不退款的语义。

## 账变语义与已验证边界

提现申请把可用积分转入冻结积分；取消申请把同一笔冻结积分退回可用余额，不是新增收入。现有实现只在审核支付时新增 `plog_type=9` 的支出账变。因此本组没有给取消申请额外增加收入账变，也没有修改 `Plog`。审核时账变返回普通错误或抛出 `Throwable`，均要求恢复冻结积分和待审核状态。

新增 `tests/security_audit_cash_refund.php` 覆盖：

- 非严格 MySQL 退款超限、余额已满、恰好达到上限、最大 65,535 提现积分和退款重放。
- 失效收款用户、冻结积分不足、零积分、未知状态和非法删除范围；审核中的对应异常也必须回滚。
- 不同用户或同一用户的批量退款，后续记录超限、状态异常或删除触发器失败时，之前的退款及删除全部回滚。
- 另一笔入账先提交后，退款必须按当前余额检查上限。
- 现有申请流程的冻结积分上溢回读保护、恰好到达冻结上限，以及取消时不影响其他冻结款项。
- 审核账变返回非异常错误、抛出 `TypeError` 或第二条账变写库失败时，全批回滚。
- 退款先完成或审核先完成的两种顺序，以及已审核重放：只产生一次退款或一次支付。
- MySQL 两个真实 PDO 连接：在第一连接已修改用户余额、尚未完成退款/审核的事务内，第二连接尝试修改提现状态和用户余额，都遭遇 InnoDB 锁等待超时（1205）。这验证现有现金记录行锁与用户更新锁能覆盖上述并发窗口；不声称是多进程压力测试。

日志位于 `/tmp/maccms-audit-20260910/cash-refund-{sqlite,mysql}-php{83,84}.log` 和 `cash-refund-framework-php{83,84}.log`。CI 建议将新测试加入现有 financial / MEMBERSHIP 套件，本组不修改 CI 或测试清单。
