# API 内容查询表前缀隔离

本组仅将 7 个 API 控制器的 19 处 `Db::table('mac_*')` 改为 `Db::name('*')`，使其使用当前连接配置的表前缀。未改变筛选条件、字段、排序、分页、权限或 JSON 协议；Vod 已修复的四个首页方法不在本组范围。

## 根因与影响

默认前缀 `mac_` 下这些查询看似正常，但自定义前缀部署会查询不存在的表；同库保留另一套 `mac_*` 表时，会返回另一套内容。文章详情主体使用配置前缀而前后篇来自固定前缀；角色详情和关联视频也可能来自两套不同数据。本组修复的是查询位置错误，不能将数据库账号可访问的不同前缀当作强租户隔离机制。

| 控制器 | 原查询位置 | 调用场景 | 数量 |
| --- | --- | --- | ---: |
| Actor | 136、189 | 详情、推荐 | 2 |
| Art | 214、216、424、474 | 前一篇、后一篇、热门、最新 | 4 |
| Manga | 243、286 | 热门、最新 | 2 |
| Role | 175 | 详情 | 1 |
| Topic | 106、120、135、201、267 | 详情、关联视频、关联文章、指定 ID 推荐、默认推荐 | 5 |
| Vod | 175、299、347、395 | 详情、年份、类型、地区筛选 | 4 |
| Website | 135 | 详情 | 1 |

共 19 个查询位置，16 个动作或分支入口。文章详情额外的主记录查询及角色关联视频查询也由回归验证与它们使用同一前缀。

## 验证

```sh
python3 tests/run_api_prefix_audit.py
```

Runner 创建一次性 MySQL，容器禁用网络并使用 Unix socket；代码目录只读挂载，不读取站点配置，也不访问业务库。回归调用真实 Request、控制器、校验器和 ORM，并解析实际 Json 响应。仅图片/链接、分类缓存和用户状态使用隔离 fixture。

- 同库建立 `audit_api_*` 与 `mac_*`，相同 ID 使用不同内容，另外设置各自独有的 ID；验证不能退回另一前缀的记录。
- 逐个覆盖全部 19 个查询位置，核对实际 SQL、选中行、详情关联、文章前后篇、正常与空分页、专题 ID 顺序及占位、三种视频筛选值。
- 删除所有 `mac_*` 表后再次执行，排除默认表掩盖遗漏；筛选每次清空隔离缓存，确保实际执行查询。
- PHP 8.3.33 / MySQL：252 项检查通过。
- PHP 8.4.25 / MySQL：252 项检查通过。

## 明确保留的独立问题

本前缀组首次提交时，Art/Manga 的 `get_latest` 仍把 TP8 Collection 传入要求 `array &$list` 的 `mac_append_type_is_vip_exclusive_for_rows()`，合法请求和空结果均会 TypeError。本组测试保留真实类型签名，在异常前从真实链接处理调用观察选中行，并检查实际 SQL；每版报告 8 次此既有故障（两接口 × 有/无记录 × 有/无默认表）。这部分只证明查询前缀正确，不表示这两个接口完整可用。随后独立的 [Collection 兼容组](api-content-collection.md) 已取消此故障分支，并强制完整 JSON 成功；上面的 252 项结果记录的是前缀组首次提交时的验证。

其他推荐列表的 Collection 加工丢失、可见性/敏感字段、参数及查询成本、旧时间条件数组和筛选缓存命名空间均需独立修复。本组不以机械替换表名前缀宣称这些边界已经解决。
