# HitsBuffer 独立修复批次

范围限定为 `application/common/util/HitsBuffer.php`，保留 `bump()` / `flush()` 的调用接口及默认关闭状态；未修改控制器、计数表结构或其他旧工具库。

## 已确认根因与处理

| 根因 | 修复 |
| --- | --- |
| `Cache::init()` 已不是当前 ThinkPHP 8 缓存接口，异常被吞掉后功能一直回退。 | 使用已安装框架的 `Cache::store()->handler()`；非 Redis、连接失败或关闭开关仍回退。 |
| 多个请求先读到各自的累计数、再分别扣减，可能重复领取已经被其他请求写入数据库的增量。 | Lua 在一个 Redis 操作内读取并删除一个字段；阈值请求与定时 flush 共用该领取逻辑。 |
| `apply()` 吞掉数据库异常，旧 flush 仍删除整份快照并报告成功，失败批次丢失。 | SQL 异常传至领取方，使用 `HINCRBY` 加回完整批次；领取后的新增计数保留。flush 只统计实际更新成功的操作。 |
| Redis 已确认接收后，后续异常返回 false 会使调用方再次直接增加一次计数。 | 跟踪是否已收到 Redis 自增确认；确认后返回 true，包括领取失败或数据库失败待重试的情况。 |
| 裸 Redis key 绕过框架配置的缓存前缀。 | 使用当前驱动的 `getCacheKey()`；默认空前缀时 key 保持一致。 |

flush 使用分批 HSCAN 枚举字段，不再重命名或整份删除快照。一个内容写入失败不阻止其他内容的落库；已删除内容的零行更新不保留无主计数，也不计入成功数。日志只记录故障阶段、内容类型/编号、批次数量及异常类名，不输出原始 SQL 或连接信息。

Lua 脚本的原子执行防止其他 Redis 命令插入读取与删除之间；这只覆盖 Redis 内部操作。[Redis Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/) HSCAN 游标可能重复返回字段，因此每次都重新原子领取当前值，不把扫描结果中的旧数值直接写入数据库。[Redis HSCAN 文档](https://redis.io/docs/latest/commands/hscan/)

## 验证

运行：

```sh
python3 tests/run_hits_buffer_audit.py
```

需要本地 `redis-server`、Docker，以及本地镜像 `mysql:8.0`、`maccms10-migration-check:latest`、`maccms-audit-php84:20260910`。可在命令后传入要测试的 PHP 镜像名。

运行器启动并销毁全新的 MySQL 容器和 Redis 进程。数据库名为随机 `maccms_audit_hits_*`，Redis 使用随机 `audit_hits_*:` 前缀及 DB 15；两个服务仅通过临时 Unix socket 使用，测试 PHP 容器设置 `--network none`，仓库只读挂载。不读取应用配置、不启动应用，也不连接已有的 `maccms_audit_models`。

PHP 8.3.33 / 8.4.25 下使用真实 ThinkPHP 缓存驱动、Think ORM、MySQL 和 Redis，各 40 项检查通过；目标类在两版本的原生 lint 均无诊断。验证内容包括：

- 开关关闭、非 Redis、连接失败、参数无效的回退；前缀隔离。
- 阈值累计、低频收尾、当前周期自增和跨周期归零。
- MySQL 触发器主动拒绝更新时完整回补；flush 返回值不伪报成功。
- 数据库更新等待期间新来的计数，与失败批次相加后恰好落库一次。
- Redis 已接收自增但 ACL 拒绝 EVAL 时保持待处理计数，并避免调用方重复自增。
- 6 个计数进程与 2 个 flush 进程竞争，视频/文章各 600 次最终都准确入库。
- 700 个独立内容跨多个 HSCAN 批次，在删除已领取字段的同时全部写入。
- 已删除内容、空缓冲和错误 Redis 数据类型的受控处理。

## 明确保留的边界

这仍是尽力而为的访问量缓冲，**不提供跨 Redis/MySQL 的 exactly-once 保证**：

- Lua 已领取、数据库尚未提交时进程崩溃，领取的批次可能丢失；没有持久化待确认队列。
- 数据库已经提交，但客户端收到的是异常或丢失回执，回补后重试可能重复计数。
- Redis 自增或领取命令的回执丢失时，客户端无法确认命令是否执行；回退可能重复，领取结果丢失可能损失批次。
- 数据库失败后 Redis 又拒绝回补，日志记录 `restore_failed`，但不能恢复已经离开 Redis 的批次。
- 日/周/月仍按实际入库时刻划分，低频或故障积压跨周期后不会还原每次访问发生的日期。
- 非空前缀部署中旧代码留下的无前缀计数不自动迁移；其归属不能从 key 本身判断。旧版本已经产生的重复/负计数和遗留快照不在本次自动修复范围内。

要消除上述进程崩溃及不确定提交窗口，需要持久化事件/领取记录和数据库去重或事务性 outbox，涉及新的存储协议及表结构，超出本批范围。
