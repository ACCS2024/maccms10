# 视频重复目录：正常保存的定向刷新

日期：2026-09-11。范围是已复现的串行保存错误，不是重复目录故障恢复、并发或迁移治理的完成声明。

## 已观察问题与修复

固定源 `fc8c07ce` 的双版本真实 MySQL 普通数据复现：两部 Before 视频中将 ID 7 改名为 Renamed，目录仍保留 `id1=7,name1=Before`；连续保存另一部无关视频，两次都返回成功，Before 目录从一条增长为两条。

原代码在 UPDATE 之后读取“旧名称”，得到的已经是新名称，因此遗漏旧组。本批在 UPDATE 前从主库读取旧名称，成功更新后分别刷新实际旧组与新组。每次针对单个名称刷新结束后，原代码又无条件 INSERT 全部重复组，造成其它组累加；现在仅保留在原有表重建分支后的全量填充，普通刷新只处理该名称。

因此，同名组的代表视频改名或回收时，目录能换成仍在组内的最小 ID；剩下一条的组退出目录；反复保存其它名称不再添加重复行。既有丢失目录表的重建行为仍会初始化完整目录，不变成只有一个名称的部分目录。

## 验证

`tests/framework_audit_vod_repeat.php` 使用真实安装 MySQL、TP8 Model/DbManager/PDO。PHP 8.3.33 / 8.4.25 各 114 项，分别覆盖非严格、NO_AUTO_VALUE_ON_ZERO、STRICT_ALL_TABLES + NO_AUTO_VALUE_ON_ZERO 三种 SQL 模式：

- 改名后旧组更换代表、组变唯一后消失、移入另一个重复组。
- 多次保存无关视频、反复刷新目标组，不累加其它目录行；刷新已有重复污染的目标组能收敛至一条。
- 回收代表和第二部视频后的实际组数。
- 缺表时原有完整重建，以及之后正常刷新不再次追加全表。
- 普通名称中的撇号继续作为绑定数据。
- 没有 DDL 和故障时，保存保留调用方事务，调用方回滚同时恢复资源与目录。

原有视频保存 438 项三模式测试也重跑。两份专项共用 `tests/fixtures/vod_save_db.php` 的真实 schema 启动逻辑，仍分进程运行。`tests/run_vod_save_audit.py` 现在在独立禁网 MySQL 中执行两份专项，现有矩阵 CI 入口继续适用。

```sh
python3 tests/run_vod_save_audit.py <php83-image> <php84-image>
```

## 明确剩余项

现有 catch 仍把一般数据库异常当作删表重建理由；DDL 可能影响调用方事务；写后目录异常与主记录保存结果尚未区分。并发刷新、表的唯一性、重建期间的读写、旧污染的整体修复、非默认连接/prefix、其它写入口和所有分类/回收写入的一致性均需下一批验证与处理。

此批没有执行生产目录重建或清理，也没有把串行通过表述为并发一致性保证。目录是派生数据，其异常仍应与主视频是否已经写入分开记录。
